# End-to-end architecture

## 1. What this system is

This is a **personal content intelligence pipeline**, not a universal scraper. Its job is to convert a set of trusted sources and user-selected links into a reviewable newsletter issue.

```text
source registry / URL inbox
          |
          v
  discovery + scheduling
          |
          v
  layered capture adapters
  RSS | API | browser/CDP | manual URL
          |
          v
  immutable raw artifacts + provenance
          |
          v
  extraction and media processing
  HTML | text | captions | audio | video metadata
          |
          v
  normalization, language detection, translation
          |
          v
  deduplication + entity/topic extraction
          |
          v
  clustering + ranking + evidence checks
          |
          v
  editorial review queue
          |
          v
  newsletter renderer + archive + search
```

The same content can enter through several paths. A Bilibili video may first arrive as a URL in the inbox, later be refreshed through the browser, and finally gain a transcript from an allowed audio download. These are separate captures of one logical item.

## 2. Collection strategy: four levels

Every source adapter declares its level and confidence.

### Level A — native feed or official API

Use this whenever possible:

- RSS/Atom feeds for websites and podcasts.
- Podcast Index for podcast discovery and metadata.
- Reddit Data API with OAuth for explicitly selected subreddits/users.
- X API for selected accounts, lists, search, or filtered streams when the economics make sense.
- Official platform APIs for content owned by the user.

Advantages: structured metadata, predictable identifiers, lower fragility, better attribution.

### Level B — source-provided public page

Fetch a public URL and extract the readable content, metadata, links, and embedded media. Cache the result and use conditional requests where possible.

Advantages: works for articles and individual posts without requiring a broad API integration.

### Level C — user-authorized browser capture

Use Playwright or another CDP client connected to the Helium browser remote-debugging endpoint. The user logs in manually; the collector navigates only to configured URLs or profiles and captures the rendered page and permitted network responses.

Recommended browser capture sequence:

1. Attach to the existing CDP endpoint; do not create or export a new cookie store by default.
2. Open a source URL supplied by the user or generated by a configured source.
3. Wait for the platform's content container, not an arbitrary fixed delay.
4. Save URL, title, author, timestamp, visible text, links, media IDs, and a small screenshot for debugging.
5. Record the adapter version and capture timestamp.
6. Close or reuse the page according to a strict rate limit.

This is a fallback for WeChat, Weibo, X, and Bilibili pages where APIs or feeds are unavailable. It is not a mechanism to defeat access controls, CAPTCHAs, paywalls, private accounts, or anti-bot systems.

### Level D — manual URL or text/audio import

The URL inbox is essential. A browser extension, bookmarklet, Telegram/desktop command, or simple form can submit a link. The pipeline then resolves and processes it. Users can also paste a passage, upload an audio file they own, or attach a transcript.

This makes the system useful even when a platform changes its page structure overnight.

## 3. Source registry and scheduling

A source is a policy object, not just a URL. It contains:

- platform and adapter name;
- feed/API/page URL;
- account, list, subreddit, channel, or show identifier;
- collection mode (`feed`, `api`, `browser`, `manual`);
- polling interval and timezone;
- language hint;
- topic hints;
- retention policy;
- maximum items and request budget;
- whether media download/transcription is allowed;
- credentials reference, never the secret itself.

Scheduling should be conservative:

- poll feeds with `ETag`/`Last-Modified` support;
- use exponential backoff on errors;
- apply per-domain and per-account limits;
- keep a dead-letter queue for failures;
- expose a pause switch per source;
- log cost and request counts for paid APIs.

## 4. Capture and raw evidence

Each capture is immutable. Store:

- canonical URL and original URL;
- source/platform and external ID;
- capture time and publication time if available;
- HTTP metadata or browser context;
- raw HTML/JSON/RSS/XML when retention is permitted;
- visible text or transcript files;
- media metadata, not automatically the media binary;
- screenshot only when useful for debugging or editorial verification;
- extraction method and adapter version;
- content hash and checksum;
- license/terms note and retention expiry.

Raw captures should be content-addressed, for example:

```text
raw/{sha256}/capture.json
raw/{sha256}/page.html
raw/{sha256}/transcript.vtt
raw/{sha256}/screenshot.png
```

Keep raw and normalized data separate. Re-running a parser must not destroy what was originally observed.

## 5. Normalization

Convert all platforms into one `ContentItem` shape (see [`CONTENT_MODEL.md`](CONTENT_MODEL.md)). Normalization should:

1. canonicalize URLs and remove tracking parameters;
2. preserve the original URL and platform URL;
3. extract author, channel/show, publication time, language, title, body, media, and quoted/replied-to content;
4. keep paragraphs and timestamps where possible;
5. detect language rather than trusting the platform hint;
6. generate a stable identity from platform ID, canonical URL, or content hash;
7. mark fields as observed, inferred, or generated.

Never overwrite source text with a translation or LLM rewrite. Store translations and summaries as derived artifacts.

## 6. Media processing

Use this priority order:

1. platform-provided transcript or caption track;
2. podcast transcript namespace or transcript URL in the RSS feed;
3. creator-provided show notes;
4. audio/video obtained through an allowed, non-circumventing path;
5. local ASR with Whisper/faster-whisper/whisper.cpp;
6. optional speaker diarization later.

For each transcript, retain timestamped segments and the ASR model/version. Chinese and English can be processed in their original languages; translation to a newsletter language is a separate derived step. Low-confidence or mixed-language segments must be flagged for review.

For long episodes/videos:

- split into bounded time windows;
- transcribe with timestamps;
- merge adjacent segments;
- remove obvious ASR artifacts without deleting the original transcript;
- create chapters and quote candidates;
- summarize from transcript segments, not from an untraceable free-form prompt.

## 7. Enrichment and editorial intelligence

Run enrichment in independent, repeatable jobs:

- language and script detection;
- title/body cleanup;
- named entities: people, companies, products, films, places;
- topic labels: technology, film, society plus later subtopics;
- claims and supporting passages;
- short summary in the source language;
- optional Chinese/English translation;
- embeddings for semantic search and clustering;
- source quality and evidence completeness;
- novelty and recency scores;
- safety/PII flags.

A generated claim should point to one or more source spans. For a podcast or video, the citation should include a timestamp. For a post thread, preserve the post ID and thread order.

## 8. Deduplication and story clustering

There are two different problems:

- **duplicate detection:** the same URL, repost, transcript, or wire story;
- **story clustering:** different sources discussing the same event or idea.

Use deterministic keys first, then similarity:

```text
same platform ID
  -> canonical URL match
  -> normalized text hash
  -> near-duplicate similarity
  -> embedding/topic cluster
```

Keep all source items inside a cluster. Select a representative only for presentation. The newsletter should show independent sources and disagreement, rather than collapsing them into one apparently authoritative statement.

## 9. Ranking

Start with an explainable score rather than an opaque recommendation model:

```text
score =
  0.30 * topic_match
+ 0.20 * source_priority
+ 0.15 * novelty
+ 0.15 * evidence_quality
+ 0.10 * recency
+ 0.10 * editorial_feedback
- penalties_for_duplicate_or_low_confidence
```

All weights should be configuration. The first version should let the user pin sources, mute sources, boost topics, and mark items useful/not useful. This feedback is more valuable than guessing the user's taste from a few issues.

## 10. Editorial review and issue generation

The first releases should be human-in-the-loop:

1. reviewer sees ranked candidates and the evidence panel;
2. reviewer accepts, edits, rejects, or defers;
3. reviewer chooses summary language and optional translation;
4. system renders an issue preview;
5. reviewer checks citations, timestamps, names, and translation;
6. issue is published to email, Markdown, and archive RSS.

Suggested newsletter item format:

- headline;
- one-sentence takeaway;
- 3–5 key points;
- why it matters to the selected topic;
- source and original-language link;
- related sources or disagreement;
- transcript/article timestamp or quoted passage;
- confidence and disclosure when AI processing was used.

Do not publish a summary when the only available evidence is a low-confidence transcript or an inaccessible source.

## 11. Storage and services

A pragmatic local-first deployment:

- **API/admin:** FastAPI;
- **workers:** Redis-backed queue or a simple scheduled worker initially;
- **database:** PostgreSQL; SQLite for a single-user proof of concept;
- **raw files:** local filesystem first, S3-compatible storage later;
- **search:** PostgreSQL full-text search first, vector extension later;
- **browser:** Playwright connected to Helium CDP;
- **extraction:** feedparser plus a readability extractor such as trafilatura/readability;
- **media:** ffmpeg and Whisper-compatible ASR;
- **delivery:** SMTP/email provider plus generated Markdown/RSS;
- **observability:** structured logs, per-adapter health, request/cost counters, and failed-capture inbox.

Keep adapters behind a common interface:

```python
class SourceAdapter(Protocol):
    def discover(self, source: SourceConfig) -> list[Candidate]: ...
    def capture(self, candidate: Candidate) -> RawCapture: ...
    def normalize(self, capture: RawCapture) -> ContentItem: ...
```

An adapter may implement only the methods its source supports. A browser adapter should never silently fall back to an unapproved scraping service.

## 12. Privacy, legal, and operational safeguards

- Prefer official APIs and feeds.
- Respect terms, rate limits, copyright, and privacy requirements.
- Do not bypass login controls, CAPTCHAs, DRM, paywalls, or geo/access restrictions.
- Do not bulk-download media by default.
- Keep platform credentials in environment variables or the OS secret store.
- Do not persist browser cookies unless explicitly enabled.
- Encrypt backups and set retention periods for raw captures.
- Store only what is needed for personal research and citation.
- Provide a delete-by-URL/source operation.
- Keep an audit trail of generated summaries and human edits.
- Treat user-generated posts as claims, not verified facts.

## 13. What “all things” means in practice

It is not technically or legally realistic to gather every post from every platform. The workable interpretation is:

- an explicit source registry for recurring sources;
- a URL inbox for anything discovered elsewhere;
- topic/search feeds where an official API permits them;
- browser capture for user-selected pages;
- podcast RSS discovery plus selected shows;
- a review queue that controls what enters the newsletter.

This gives broad coverage without building an unreliable surveillance crawler.

## 14. First vertical slice

The first working slice should be deliberately small but prove the whole method:

1. Add RSS feeds and podcast feeds from YAML.
2. Accept arbitrary URLs through a CLI or local API.
3. Capture one public article and one Reddit item.
4. Connect to a Helium browser page and capture one user-selected WeChat/X/Weibo/Bilibili URL.
5. Normalize all four into `ContentItem` records.
6. Deduplicate, summarize, and cite each item.
7. Generate one Markdown newsletter preview.

Only after this works should we add recurring browser crawls, broad account search, audio downloads, or autonomous publishing.
